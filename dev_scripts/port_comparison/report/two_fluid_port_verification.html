nozzle-hyperbolic · two-fluid model · 3 November 2026

Two-Fluid Port Verification

Comparison of the refactored TwoFluidModel (repository nozzle-hyperbolic, main at e318cc0) against Alberto's original solver (alberto-branch, commit faafff7, the port's declared source). Prepared for Roberto. No code was modified in either repository for this comparison.

Physics port verified

The new implementation reproduces the old residual to round-off (about 1e-10 relative) for every physics path and option used by the NICFD cases. Converged solutions agree to 0.1 % with Van Leer reconstruction. The remaining differences are numerical choices, changed defaults and a few unported features, listed in section 6. With the old property tables, the new solver converges the flashing-water adapted case in 55 implicit steps. This points to the regenerated tables, not the solver, as the main suspect for the failed NICFD flashing runs.

1 · Method

How the codes were compared

Both codes ran in the same Python interpreter with the same editable JAXProp checkout; only PYTHONPATH changed between them. Both used the same EOS tables, the old branch's dev_scripts/fluid_tables pickles.

To compare discretizations directly, the new model was built on a Mesh that reproduces the old layout. Cell centres are the old interior points x[1:-1], faces are their midpoints, face areas are the old averages 0.5(A_i + A_i+1), and volumes are A·dx. On this mesh the old interior cells and the new physical cells coincide one to one.

Three levels of comparison were run:

  1. Residual. The old _residual (from make_two_fluid_step(..., return_debug=True), dt = 1, Wn = W) against Operator.physical_spatial_residual on identical states. The states were taken from the NICFD reference profiles.
  2. Boundary equations. The old converged ghost rows stored in the six NICFD references were inserted into the new boundary_residual.
  3. Converged solutions. Both solvers ran to steady state with the same grid, settings and restart profile.

Two details from this step

  • Van Albada. The old limiter had a magnitude-scaled regularization, eps = va_rel·(|U_i| + 0.1·mean|U|) with va_rel = 1e-3. The new numerics.reconstruction.van_albada has none. This is a numerical change, already listed in the NICFD case's differences field.
  • Filter at the first and last interior faces. The old code builds the filter's third difference from Wn ghost rows (the stored ghost) while its fluxes use the freshly applied BC ghost. The new code uses the current trace for both. The two agree once the stored ghost equals the BC ghost, which is always true at steady state. With inconsistent ghosts in a test state they differ at the two boundary faces only.

Van Leer. The interior residual is identical here, so the remaining 0.1 % comes from where the boundary data sit. The old ghost lies one cell outside; the new trace sits on the end face, which also changes the slope of the first and last cells. In subsonic flow this moves the whole profile slightly. It is a numerical difference that vanishes with refinement.

Van Albada. The larger difference is the limiter change. Inside each code, switching Van Leer to Van Albada moves α by 0.78 % in the old solver but only 0.06 % in the new one. The new Van Albada behaves almost like Van Leer.

What this says about the failed NICFD flashing runs

With the old tables the new solver converges this case without difficulty: CFL ramps to about 7900 with 2 Newton iterations per step. The NICFD campaign in the repository used regenerated tables (liquid hmin raised to 250 kJ/kg) on the new mesh convention, starting at 100 cells. The tables are the main suspect, but this run does not prove it. The next check is the same run with only the tables swapped.

5 · Reference provenance

The NICFD reference profiles predate the current source terms

The reference.csv files in cases/NICFD2026 were produced with revision e185f57 (28 September). Commit faafff7 (29 October), which the port is based on, added the closure-driven interfacial pressure work to both algebraic source assemblies, D_VE_algebric and D_VE_algebric_two_component:

T_k·Ṡ_k = σ_Mk[(h_ex,k − h_k) + ½(u_ex − u_k)²] + F_k(u_int − u_k) + σ_Qk M_k = σ_Mk + (Γ_k / a_k²)·T_k·Ṡ_k (volume production of phase k at fixed p) Dα = (a₀² / ρ_s)·( α_l·M_g / a_l² − α_g·M_l / a_g² ) E_g row: −p·Dα E_l row: +p·Dα (mixture energy unchanged)

The area-driven part of p·∂α/∂t was already in D_VE_area; this adds the part driven by mass transfer, heat and drag work. With it, the algebraic source equals the independent conservative transform D_VE_conservative to 1e-16 in all six rows; without it the energy rows disagree.

Its size on the reference states is at most 0.2 % of the per-phase energy source in the two-component cases. In flashing it is 0.8 % (median) and 6 % (maximum, near α ≈ 0.3). Mostly it shifts the energy split between phases, which the evaporation gate reads.

The port contains the term, as it should. The consequence is for validation: agreement with the September references is not an independent check of the current physics in either code. The rerun old solver differs from the flashing-adapted reference by up to 0.8 % in p and α and 4.9 % in hg. Two intermediate corrections (e642974, fda8ac3) were commented out again in faafff7; the port correctly omits them.

7 · Property tables

Newly generated tables differ at invalid edge rows

demos/two_fluid/run.py fails in liquid.get_state(PT_INPUTS, 20 bar, 295.15 K) (optimistix root find, non-finite input). JAX reports the error asynchronously, so the traceback points at the gas line.

The water table the demo generated (water_145x200.pkl, editable JAXProp at 74794ec) differs from the old table of the same name almost only in the first enthalpy row (hmin = 1 kJ/kg) at pressures above about 10 bar. That row lies below the freezing line, where CoolProp returns invalid states. The two generator versions fill it differently: for example, the tabulated T at (hmin, pmax) is 6e-5 K in the old table and 1.56 K in the new one. Neither table contains NaNs. The PT inverse fails on the new table and succeeds on the old one (h = 94.1 kJ/kg); the nitrogen table is unaffected.

The NICFD flashing setup's switch to a 250 kJ/kg liquid hmin, made because of copied metastable stencils, is likely the same class of problem. Suggested fixes: raise the liquid hmin above about 10–20 kJ/kg for the N₂–water demo, and review how recent JAXProp changes fill invalid edge states (225f8ef, d68d5e3, 74794ec).

8 · Next steps

Suggested follow-up

  1. Rerun the flashing adapted case with the new solver and the repository's regenerated tables, everything else as in section 4. This separates the table effect from the mesh and setup effects.
  2. Repeat on the NICFD case mesh (exact areas, traces on [0, L]) and from 100 cells upward, as in the campaign.
  3. Regenerate the NICFD references with the current source terms before using them as acceptance data.
  4. Decide on the Van Albada variant and on a documented preset reproducing the old YAML defaults.
  5. Port the per-cell ai_scale field for the data-assimilation work.

Environment: Python 3.12.3, JAX 0.6.2, editable JAXProp at 74794ec (labelled 0.5.6), Windows 11. Tables: old-branch dev_scripts/fluid_tables unless stated.

Comparison scripts (residual evaluation, boundary check, end-to-end drivers and plots) are kept outside both repositories and are available on request.
